## 1. 模块详细设计

### 1.1 指纹

#### 1.1.1 文件列表规范化

输入为种子的 info 字典（v1、v2 或混合）。

```
fn normalized_entries(info) -> (Vec<(Bytes, u64)>, root_name):
    root_name = NFC(info.name)
    if v1 单文件（info.length 存在）:
        return [(NFC(info.name), info.length)], root_name      # 单文件：文件名参与（FR-XSP-002）
    files = v1: info.files；v2-only: 深度优先遍历 info["file tree"]，按字节序遍历键
    out = []
    for f in files（保持种子中的顺序）:
        if f.attr 含 'p' 或 path[0] == ".pad": continue        # BEP 47 填充文件
        p = 用 "/" 连接 [NFC(c) for c in f.path]                # 不含根目录名
        if p 为空、含 "." 或 ".." 组件、含 NUL: return Err(InvalidPath)
        out.push((utf8(p), f.length))
    if out 为空: return Err(Empty)
    return out, root_name
```

- 路径组件必须是合法 UTF-8；如果存在 `path.utf-8` 就优先使用；都不是合法 UTF-8 时视为无效种子，不参与辅种。
- 大小写不做折叠；路径分隔符统一为 `/`。

#### 1.1.2 结构指纹 SFP

```
SFP = H( "xseed/sfp/v1" ‖ 0x00 ‖ u32be(n) ‖
         for (p, len) in entries: u32be(|p|) ‖ p ‖ u64be(len) )
```

#### 1.1.3 内容指纹

| 名称 | 定义 | 用途 |
|---|---|---|
| CFP1 | `SHA1(info.pieces)`（兼容 NexusPHP 的 `pieces_hash`） | 证明 v1 内容一致（同 piece 大小） |
| CFP2 | `H("xseed/cfp2/v1" ‖ 按 entries 顺序拼接每个文件的 pieces root)`（长度 ≤ 16 KiB 的文件以文件内容的 SHA-256 叶子根代替，按 BEP 52 计算） | 证明 v2 内容一致（与 piece 大小无关） |

两个种子满足 `SFP` 相同且（`CFP1` 相同或 `CFP2` 相同），即判定为“内容已证明一致”，加种时不读盘。

#### 1.1.4 位置键与桶

```
L      = H("xseed/loc/v1" ‖ SFP)
bucket = u16be(L[0..2])              # 0..65535
```

### 1.2 本地清单（inventory）

```
loop every 10 min or on downloader event:
    for t in downloader.list_completed():            # 进度 == 1.0
        if t.state ∉ {seeding, stalledUP, stoppedUP, pausedUP, queuedUP, forcedUP}: skip
        if known(t.info_hash) and t.unchanged: continue
        meta = downloader.export(t.info_hash)        # .torrent 原始字节
        (entries, root) = normalized_entries(meta.info) else mark invalid
        for (p, len) in entries: stat(map_path(t.save_path, root, p)).len == len else mark missing
        site = sites.identify(downloader.trackers(t))   # §1.11
        upsert local_torrents(sfp, cfp1, cfp2, site_ref, hosts, …)
```

`map_path` 按配置的 `path_map` 把下载器路径换成 agent 路径（§4）。统计文件大小只读元数据，不读内容（NFR-XSP-004）。

### 1.3 节点选择与 HRW

```
fn owners(bucket, nodes_with_role_index, R=2) -> [node]:
    for n in nodes:
        u = (u64be(H("xseed/hrw/v1" ‖ n.id ‖ u16be(bucket))[0..8]) + 0.5) / 2^64   # (0,1)
        score[n] = -ln(u) / n.effective_weight
    return 取 score 最小的 R 个
effective_weight = manifest.weight × ramp(age)        # ramp：上线 14 天内从 0.1 线性升到 1.0
```

信箱节点的选择：在声明了 `home` 角色的节点中，取最近 3 次 RTT 的中位数最小者；连续 3 次失败后降级 1 小时。用户可以固定使用某个节点。

### 1.4 两跳登记与查询

#### 1.4.1 封装

- HPKE（RFC 9180）：`DHKEM(X25519, HKDF-SHA256)`、`HKDF-SHA256`、`ChaCha20Poly1305`，Base 模式，`info = "xseed/ohttp/v1" ‖ target_node_id`。
- 请求：`enc ‖ ct`；响应：用 HPKE 导出的密钥 `export("xseed/ohttp/resp", 32)` 加 `ChaCha20Poly1305`（nonce 随机 12 字节，放在密文前）。
- 信箱节点只看到目标节点 ID 和密文长度；按 256 字节的倍数填充，减少长度泄露。

#### 1.4.2 操作

| 操作 | 明文（CBOR） | 说明 |
|---|---|---|
| `REGISTER` | `{op:1, reg_id:bytes16, mbox:MailboxAddr, buckets:[u16], ttl_s:u32, pow:Pow}` | `reg_id` 是 agent 为每个 index 节点生成的稳定随机值；同一 `reg_id` 的新登记**整体替换**旧集合；`buckets` 只含 HRW 归属该节点的桶 |
| `UNREGISTER` | `{op:2, reg_id, proof:HMAC(reg_secret, "unreg")}` | `reg_secret` 在首次登记时随请求发送，节点只存其 hash |
| `LOOKUP` | `{op:3, buckets:[u16] (≤64)}` | 返回 `{bucket: [MailboxAddr]}`，每个桶最多 64 条，按最近登记时间排序 |

`MailboxAddr = {node:bytes16, mbox:bytes16}`，不含任何 IP 信息。

#### 1.4.3 home 节点同时是 index 节点时

agent 计算某个桶的归属节点集合时，如果其中包含自己的 home 节点，对这个目标节点的请求改为经“延迟次低的另一个 home 节点”转发，以防同一个节点同时看到 IP 和桶。

### 1.5 会话与加密

#### 1.5.1 探测

```
K_probe = HKDF(SFP, "xseed/probe/v1", "", 32)
nonce   = random(16)
tag     = HMAC(K_probe, nonce ‖ reply_to.node ‖ reply_to.mbox)[0..16]
PROBE   = {t:"probe", v:1, bucket, nonce, tag, reply_to, sid:random(16)}
```

应答方按 `bucket` 找出本机的候选 SFP（同一个桶里通常只有个位数），逐个计算 tag 并做常量时间比较；匹配到就回 `PROBE_ACK{sid}`，否则不回应（不暴露“桶中有内容但不匹配”）。

#### 1.5.2 Noise 握手

- 模式：`Noise_XXpsk3_25519_ChaChaPoly_BLAKE2s`（`snow`）；查询方为发起方。
- `psk = HKDF(SFP, "xseed/psk/v1", "", 32)`；prologue = `"xseed/v1" ‖ sid`。
- 静态密钥每个会话重新生成，不同会话之间不可关联。
- 握手完成后取握手 hash `h`（32 字节），派生 `K_cb = HKDF(h, "xseed/cb/v1", "", 32)`，作为所有锁答案的绑定密钥。
- 传输消息：每条 Noise 消息 ≤ 65535 字节；应用层分帧为 `u16be(len) ‖ cbor`。

#### 1.5.3 会话状态机

```
Init ─PROBE→ Probing ─ACK→ Handshaking ─3 条消息→ Lock2 ─双向通过→ Lock3 ─至少一个共同站点通过→ Offering
     ─(有种子文件要传)→ Upgrading ─直连成功→ Bulk(direct) │ 失败或配置为不直连→ Bulk(relay) ─→ Done
任一状态：超时、校验失败、收到 ERROR → Closed(reason)
```

| 阶段 | 超时 |
|---|---|
| Probing | 15 s |
| Handshaking | 20 s |
| Lock2 | 30 s（含读盘） |
| Lock3 | 90 s（含 scrape 或下载挑战） |
| Upgrading | 5 s |
| Bulk | 60 s |
| 整个会话 | 300 s |

### 1.6 三道锁

#### 1.6.1 锁 1：文件暗号

由探测 tag 加 Noise psk 实现：不知道 SFP 的一方无法生成有效 tag，也无法完成握手。

#### 1.6.2 锁 2：持有证明（双向）

```
challenger:
    total = Σ len(entries)
    ranges = 3 个 (offset, 16384)，offset 均匀随机于 [0, total-16384]；total < 49152 时退化为 1 个覆盖全文的区间
    send LOCK2_CHAL{ranges}
prover:
    data_i = read(concat_stream, range_i)               # 按 entries 顺序拼接的虚拟字节流
    send LOCK2_ANS{macs:[HMAC(K_cb, "xseed/l2/v1" ‖ u64be(off) ‖ data_i)]}
challenger: 用本机数据计算同样的 HMAC，逐个常量时间比较
```

双方各出一次题、各答一次，**两个方向都通过**才进入锁 3。读盘量为 3 × 16 KiB。

#### 1.6.3 锁 3：会员验证

对每个**可能的共同站点**独立判定。按优先级选择方式（同一站点只用第一种可用的方式）：

**（A）群组密钥（站点在注册中心标记 `group_key: true`，且本机已领取密钥）**

不需要声明。双方各自对本机持有该内容的每个群组密钥站点生成报价，**不标站点名**，打乱顺序后发送：

```
K_offer(site, epoch) = HKDF(GK(site, epoch), "xseed/offer/v1", h ‖ SFP, 32)
OFFER_SEALED = AEAD_ChaCha20Poly1305(K_offer, nonce=random(12), aad="xseed/offer/v1", OfferMeta)
```

接收方用本机持有的每把（当前、上一周期）群组密钥逐个尝试解密，能解开就说明双方是同站会员。密钥里混入了 `h`，所以中间人转发的密文另一侧解不开；非会员即使拿到密文也打不开。

**（B）scrape 挑战（tracker 支持带 passkey 的 scrape）**

```
A → B: CLAIMS{hosts:[TrackerHost] ≤ 16}        # A 在本内容上可能需要的、非群组密钥站点的 tracker 主机
B: common = CLAIMS ∩ B 持有本内容的站点主机
for host in common:
    B 从自己在该 host 上的**其他**种子中随机选一个 T（排除本内容），并缓存自己的 scrape 结果 d_B
    B → A: L3_SCRAPE_CHAL{host, info_hash: T}
    A：用本机 passkey scrape → d_A = files[T].downloaded
    A → B: L3_SCRAPE_ANS{host, macs: shuffle([HMAC(K_cb, "xseed/l3s/v1" ‖ host ‖ T ‖ u64be(v)) for v in d_A-2 ..= d_A+2])}
    B：计算 HMAC(K_cb, … ‖ u64be(d_B))，检查是否在 macs 中
```

反方向（B 也要从 A 那里拿报价）对称执行。B 在 scrape 返回失败时，把该 host 记为 `scrape=unsupported`（§1.12），本次改用（C）。

**（C）下载挑战（站点有可用的下载地址，§1.8.3）**

```
B → A: L3_DL_CHAL{host, torrent_id: I}          # B 在该站的其他种子
A：用本机凭证下载 I，计算 info_hash ih
A → B: L3_DL_ANS{host, mac: HMAC(K_cb, "xseed/l3d/v1" ‖ host ‖ ih)}
B：用本机记录的 I 对应的 info_hash 校验
```

**都不可用：** 该站点不交换；用户可以对单个 host 开启 `lenient = true`，只要求锁 1 和锁 2。

#### 1.6.4 通道绑定的安全性论证

设中间人 M 与 A 建立会话（握手 hash 为 h₁），与 B 建立会话（h₂）。M 需要知道 SFP 才能完成两次握手，并且需要持有数据才能通过锁 2。

- 锁 2：A 的答案是 `HMAC(HKDF(h₁), …)`，在 h₂ 下校验必然失败；M 只能自己读数据作答，而这只能证明 M 自己持有数据。
- 锁 3（A）：`K_offer` 混入了 h，M 转发的密文在另一侧解不开；M 要自己生成报价，就必须持有群组密钥，也就是 M 本身就是会员。
- 锁 3（B）、（C）：答案混入了各自会话的 h；M 要产生在 h₂ 下有效的答案，就需要自己的 passkey 或下载能力，同样意味着 M 本身就是会员。

结论：中间人最多只能以自己的真实身份参与，无法借用他人的身份（FR-XSP-006）。

#### 1.6.5 残余风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| R1 声明泄露 | `CLAIMS` 会让通过了锁 2 的对端（他持有同样的内容）知道你在哪些 tracker 有账号 | 上限 16 个；只声明“本内容可能用到的”主机；优先使用群组密钥 |
| R2 挑战种子泄露 | scrape 挑战会把一个其他种子的 info_hash 交给通过了锁 2 的对端 | 每个对端每个 host 每天最多 1 次；在报价阶段才发；对端拿不到你的 IP（§1.7），单独拿到 info_hash 无法绕过 tracker |
| R3 会员滥用 | 真实会员可以拿到其他会员的报价 | 这是辅种本身的目的，不属于风险 |

### 1.7 传输

#### 1.7.1 信箱信封

信箱 WebSocket 上的每一帧都是一个 CBOR 信封：

```
Envelope = {
  v: 1,
  to:   MailboxAddr,
  from: MailboxAddr,        # 回信地址
  sid:  bytes16,
  kind: "probe" | "probe_ack" | "noise" | "bulk" | "close",
  body: bytes               # probe 为 PROBE CBOR；noise / bulk 为 Noise 密文
}
```

节点间投递 `/v1/fwd` 的请求体为 `{env: Envelope, origin: node_id, ts, sig: Ed25519(origin_sk, "xseed/fwd/v1" ‖ H(cbor(env)) ‖ ts)}`。接收节点用注册中心中 origin 的公钥验签，时间差超过 60 s 就拒收。

#### 1.7.2 验证后直连

条件：锁 3 至少一个站点通过，**且**双方配置均不是 `ip_exposure = never`，**且**有清洗后的种子需要传输。

```
双方：在同一个 UDP 端口上启动 quinn Endpoint（同时作为客户端和服务端）
      向 STUN 服务器做 Binding，得到映射地址；收集候选地址：STUN 映射地址、全局 IPv6；LAN 地址仅在配置允许时加入
      生成本会话的自签证书（rcgen，Ed25519），计算 SPKI SHA-256
双方经 Noise 通道交换 UPGRADE{candidates, cert_fp}
应答方：向查询方每个候选地址每 200 ms 发 1 个 UDP 打洞包，持续 5 s
查询方：并发向应答方每个候选地址发起 QUIC 连接；ALPN = "xseed/1"；只接受证书 SPKI 等于 cert_fp 的连接
首个成功的连接胜出，关闭其余连接；5 s 内都不成功就回退到信箱中继
```

直连上只传 `Bulk` 帧，格式与经 Noise 传输时相同（QUIC 的 TLS 已提供机密性，`cert_fp` 由 Noise 通道认证，等价于继承了 Noise 的身份认证）。

#### 1.7.3 代理与 Tor

- `transport.proxy = "socks5h://…"`：信箱 WebSocket、注册中心拉取、STUN 之外的全部节点流量都走代理；同时强制 `ip_exposure = never`。
- `transport.tor = "embedded"`（P2，feature `tor`）：内嵌 arti 客户端，效果同上。
- 代理不可用时**不回退到明网**，直接报错，并在 Web UI 显示。

### 1.8 报价与取种

#### 1.8.1 OfferMeta

```
OfferMeta = {
  site: SiteRef,                       # {kind:"site", id} | {kind:"host", host}
  hosts: [TrackerHost],                # 该种子的全部 tracker 主机（已规范化）
  ih1: bytes20?, ih2: bytes32?,        # info_hash
  torrent_id: text?, details_url: text?,
  has_torrent: bool,                   # 是否会随后在 Bulk 阶段发送清洗后的种子
  size: u64
}
```

`details_url` 只保留 `scheme://host/path`，加上白名单参数 `id`、`torrentid`、`tid`。

#### 1.8.2 种子清洗（应答方）

```
fn sanitize(raw: &[u8]) -> Result<Vec<u8>>:
    root = bdecode(raw)；info_raw = 原始字节切片 root["info"]       # 保留原始字节，不重新编码
    out = BDict::new()
    out["info"] = info_raw
    out["announce-list"] = [[host_only(u) for u in tier] for tier in announce_list or [[announce]]]
    out["announce"] = out["announce-list"][0][0]
    for k in ["creation date", "created by", "encoding"]: if k in root: out[k] = root[k]
    if "comment" in root:
        c = clean_urls(root["comment"])                    # 规则同 details_url
        if not re.search(r"[A-Za-z0-9]{24,}", c): out["comment"] = c   # 疑似令牌就整条丢弃
    result = bencode(out)
    assert info_hash(result) == info_hash(raw)
    return result
host_only(u) = scheme ‖ "://" ‖ host ‖ (":" ‖ port 若非默认端口)
```

`url-list`、`httpseeds`、`nodes`、其他任何顶层键一律丢弃（防止用户名、用户 ID 等水印泄露）。

#### 1.8.3 取种（查询方）

```
fn obtain(offer, bulk_torrent?) -> Torrent:
    trait = traits.get(host, "torrent_source")   # peer | site，默认 peer
    if bulk_torrent and trait != site and !per_torrent_key(host):
        own = local announce-list for host（取本机该 host 最近一次 tracker 状态正常的种子）
        if own: return rebuild(bulk_torrent, own)        # 只替换 announce / announce-list
    url = sites.download_url(offer)                       # §1.11.3
    if url: return http_get(url) with site rate limit
    Err(NoSource)

fn per_torrent_key(host): 本机该 host 下 ≥ 2 个种子的 announce 地址去掉 passkey 后仍然不同
```

加入下载器后，如果首次 announce 返回认证失败或 “unregistered”，就移除种子（不删文件），把 `torrent_source = site` 写入 `host_traits`，然后按回退路径重试一次。

### 1.9 校验与抽查

```
verify(t, local):
    require ih(t) == offer.ih1 / ih2
    require SFP(t) == local.sfp
    if CFP1(t) == local.cfp1 or CFP2(t) == local.cfp2: return Proven
    return sample(t, local)

sample(t, local):
    pieces = ∅
    for each file f in entries(t):
        pieces += piece_index(f.start) ∪ piece_index(f.end - 1)
    pieces += 2 个随机 piece
    if |pieces| > 32: 优先保留小文件的首尾 piece，截断到 32
    for p in pieces: SHA1(read(local, piece_range(t, p))) == t.pieces[p] else return Mismatch
    return Sampled
```

信任本机状态的前提（加入前再检查一次）：原种子进度 == 1.0、状态属于做种类、每个文件 `stat` 大小一致。

### 1.10 下载器适配与安全规则

```rust
#[async_trait]
pub trait Downloader {
    async fn list_completed(&self) -> Result<Vec<LocalTorrent>>;
    async fn export(&self, ih: &InfoHash) -> Result<Vec<u8>>;
    async fn trackers(&self, ih: &InfoHash) -> Result<Vec<TrackerEntry>>;   // url、tier、status、msg
    async fn add(&self, req: AddRequest) -> Result<()>;
    async fn status(&self, ih: &InfoHash) -> Result<Option<TorrentStatus>>;
    async fn start(&self, ih: &InfoHash) -> Result<()>;
    async fn remove_keep_data(&self, ih: &InfoHash) -> Result<()>;          // 没有任何删除数据的接口
}
pub struct AddRequest { torrent: Vec<u8>, save_path: PathBuf, root_rename: Option<String>,
                        tags: Vec<String>, category: Option<String> }
```

| 规则 | qBittorrent 实现 | Transmission 实现 |
|---|---|---|
| 停止状态加入 | `stopped=true`（5.x）/ `paused=true`（4.x） | `paused=true` |
| 跳过校验 | `skip_checking=true` | RPC 无对应参数（实现时核实 TR 加入时是否自动校验） |
| 不自动管理 | `autoTMM=false`，显式 `savepath`，`contentLayout=Original` | `download-dir` |
| 标记 | `tags=xseed` | `labels=["xseed"]`（TR ≥ 4.0） |
| 移除 | `torrents/delete?deleteFiles=false` | `torrent-remove`，`delete-local-data=false` |
| 只操作自己加入的 | 移除、启动前检查 `added_torrents` 中有记录**并且**带 `xseed` 标签 | 同左 |
| 幂等 | 加入前检查 info_hash 是否已存在 | 同左 |

`remove_keep_data` 在实现层面硬编码 `deleteFiles=false`，并有单元测试断言请求参数。

**布局：**

| 情况 | 处理 |
|---|---|
| 根目录名相同 | 直接使用原种子的 `save_path`，不建链接 |
| 根目录名不同、同一文件系统 | 在 `link_dir/<info_hash>/` 下按新种子结构建硬链接 |
| 跨文件系统且支持 reflink | `FICLONE` |
| 其他 | 放弃，原因写为 `cross_device` |

### 1.11 站点识别

#### 1.11.1 主机规范化

`TrackerHost = lowercase(IDNA-ASCII(host)) ‖ (":" ‖ port，若不是 scheme 的默认端口)`。只保留 http、https、udp 三种 scheme。

#### 1.11.2 匹配

```
fn identify(trackers) -> SiteRef | Ambiguous | None:
    hosts = {normalize(t.url) for t in trackers} − public_trackers   # 注册中心提供公共 tracker 列表
    sites = {s | ∃ h ∈ hosts: h ∈ s.tracker_hosts or h 以 "." ‖ d 结尾（d ∈ s.domains，默认规则）}
    if |sites| == 1: return Site(s)
    if |sites| > 1: return Ambiguous           # 不登记、不查询
    if |hosts| ≥ 1: return Host(min(hosts))    # 无站点定义：以 tracker 主机为身份
    return None
```

以 `Host` 身份交换时，只要双方 `hosts` 有交集，就视为同一站点。

#### 1.11.3 下载地址

依次尝试（成功的模板写入 `host_traits.download`）：

1. 站点定义的 `download_template`（导入 PT-depiler 时按框架生成）；
2. 无站点定义时，用 `details_url` 的主机按通用模板试：NexusPHP `https://{host}/download.php?id={id}&passkey={passkey}`；
3. 都失败就放弃，Web UI 提示为该站配置 Cookie 或 API token。

`{passkey}` 来自本机该 host 已有种子 announce 地址中的 `passkey`、`authkey`、`torrent_pass` 参数，或者路径中的 32 位十六进制段。

### 1.12 站点特性学习

| `download` | 模板字符串 | 按 §1.11.3 下载成功 | 30 天 |

优先级：本机学到的 > 注册中心发布的 > 默认值。`xseed-agent traits export` 输出 YAML（只包含 host、特性、取值、证据类型与时间，不含任何凭证或种子信息）。

## 2. 接口详细设计

### 2.1 节点 HTTP 接口

#### `GET /.well-known/xseed`

```json
{"proto":[1],"node_id":"3f2a…","roles":["home","index"],"load":0.42,
 "time":1793952000,"challenge_sig":"…"}
```

`?challenge=<hex32>` 时，`challenge_sig = Ed25519(sign_sk, "xseed/wk/v1" ‖ challenge)`，供 CI 验证节点确实持有清单中的密钥。

#### `POST /v1/mailbox`

请求：`{pow: {salt: bytes16, nonce: u64, bits: u8}}`。工作量证明要求 `H("xseed/pow/v1" ‖ server_salt ‖ salt ‖ u64be(nonce))` 至少有 `bits` 个前导零比特；`server_salt` 来自 `/.well-known/xseed`，每小时轮换；`bits` 默认 20，节点负载高时可以提高到 24。
响应：`{mbox: bytes16, secret: bytes32}`。节点只保存 `H(secret)`。
限流：每个 IP 每天 10 个。

#### `GET /v1/mailbox/ws`

鉴权：建立连接后服务端发送 `{challenge: bytes32}`，客户端回复 `{mbox, mac: HMAC(secret, "xseed/ws/v1" ‖ challenge)}`。
之后双方收发 Envelope（§1.7.1）。心跳：每 30 s 一次 WebSocket ping；90 s 无响应就断开。
同一信箱只允许 1 条连接，新连接会踢掉旧连接。

#### `POST /v1/ohttp`

请求：`{target: node_id, req: bytes}`（≤ 64 KiB）。home 节点以 `/v1/gateway` 转发给目标节点，把原始响应字节透传回来。home 节点不解析 `req`。

#### `POST /v1/gateway`

请求：`{req: bytes}`。index 节点用 `hpke_sk` 解封装，执行 §1.4.2 中的操作，返回封装后的响应。

#### `POST /v1/fwd`

请求：§1.7.1 中的签名结构。目标信箱不在线时返回 `404 xseed.node.mailbox_offline`，**不暂存**。

#### 限流与配额（默认值）

| 对象 | 限制 |
|---|---|
| 每个信箱发出的探测 | 60 次/分钟 |
| 每个信箱收到的探测 | 120 次/分钟，超出直接丢弃 |
| 每个来源节点的 `/v1/fwd` | 2000 次/秒 |
| 每个会话的中继流量（验证前） | 64 KiB |
| 每个会话的中继流量（回退中继，验证后） | 4 MiB |
| 每个信箱每天的中继总量 | 256 MiB |


`peer_hash = H("xseed/peer/v1" ‖ MailboxAddr)`；凭证用 XChaCha20-Poly1305 加密，密钥来自系统密钥环，无密钥环（Docker）时由 `XSEED_VAULT_PASSPHRASE` 经 Argon2id 派生。

数据量：每台设备 3000 个种子时，`local_torrents` 约 3000 行，`offers` ≤ 3 万行，SQLite 文件 < 50 MiB（主要是种子 BLOB，单个 ≤ 2 MiB，超过的只保存元数据）。

### 3.2 node 内存结构

```rust
struct Mailboxes { map: DashMap<MboxId, Mailbox> }          // secret_hash, conn: Option<Sender>, last_seen
struct Index {
    regs:    DashMap<RegId, Reg>,                              // mbox_addr, buckets: Box<[u16]>, expires, secret_hash
    buckets: Box<[RwLock<Vec<(RegIdx, MailboxAddr)>>; 65536]>,// 倒排；每个桶上限 4096 条，超出淘汰最旧的
}
```

内存估算（1 万台设备，每台 3000 个桶，副本数 `R = min(2, N)`，N 个 index 节点）：每个节点约 `1e4 × 3000 × R / N` 条倒排记录。如果每条记录直接保存 `MailboxAddr`（约 40 字节），N=1 时约 1.2 GiB，**超过 1 GiB**。因此倒排记录采用紧凑表示：`RegIdx: u32` 指向 `regs` 的槽位表，`MailboxAddr` 只保存在 `Reg` 中，每条倒排记录 4 字节；N=1 时约 120 MiB，加上 `Vec` 的容量冗余，按 240 MiB 计（满足 NFR-XSP-001）。

快照：收到 SIGTERM 时把 `regs` 写成 bincode 文件（含过期时间），启动时载入并重建倒排表。快照不包含信箱密钥 hash 以外的信息。

## 6. 安全设计

| 项 | 措施 |
|---|---|
| 密码学原语 | X25519、ChaCha20-Poly1305、BLAKE2s（Noise）；SHA-256、HKDF、HMAC；Ed25519；HPKE（RFC 9180）；均使用经过审计的 crate，禁止自研 |
| 常量时间比较 | 所有 MAC、tag 比较使用 `subtle` |
| 输入校验 | bencode 解析限制：嵌套深度 ≤ 32、单个种子 ≤ 16 MiB、文件数 ≤ 100000；CBOR 解码限制：单条消息 ≤ 64 KiB、数组 ≤ 4096 个元素 |
| 路径安全 | 拒绝绝对路径、`..`、NUL；建链接前做 `canonicalize`，并确认结果位于 `link_dir` 内 |
| 凭证 | 只在本机加密存储；日志脱敏规则：URL 查询参数整体替换为 `?…`，32 位以上的十六进制串打码 |
| 清洗 | §1.8.2 白名单；`info` 原始字节不重新编码；单元测试覆盖 passkey 在路径、查询串、comment 中的各种情况 |
| 下载器 | 只有 `remove_keep_data`，没有删除数据的代码路径；操作前检查 `added_torrents` 和标签 |
| 节点 | 不记录信封内容；访问日志默认关闭 IP 字段；工作量证明与限流防止批量注册 |
| 供应链 | 可复现构建（`cargo auditable`、锁定工具链）；发布物 minisign 签名；不静默自动更新 |
| 威胁与对策 | 见 02 §1.2、本文 §1.6.4–1.6.5、00-落地设计 §5 |

## 7. 性能设计

### 7.1 节点容量（1 万台设备，每台 3000 个种子，每天新增 20 个）

| 资源 | 估算 |
|---|---|
| 信箱连接 | 1 万条 × 约 10 KiB = 100 MiB |
| 桶倒排（单个 index 节点承担全部） | 约 240 MiB（§3.2） |
| 登记 `regs` | 1 万 × 3000 × 2 字节 ≈ 60 MiB |
| CPU | 心跳约 330 条/秒；查询约 2.3 次/秒；HPKE 解封装每次约 50 µs |
| 重连风暴 | 客户端在 0–120 s 内随机延迟重连；TLS 握手每次约 1 ms，单核约 1000 次/秒 |

### 7.2 流量

| 阶段 | 单次会话 | 1 万台设备 / 天（3 个对端 × 20 个新种子） |
|---|---|---|
| 探测 + 握手 + 锁 2 + 锁 3 + 报价元数据（经两个信箱节点） | 约 6 KiB × 2 跳 | 约 7 GiB，分摊到所有 home 节点 |
| 种子文件（直连成功） | 0（不经节点） | — |
| 种子文件（回退中继，估计占 15%） | 平均约 150 KiB × 2 跳 | 约 25 GiB |

### 7.3 agent

- 清单扫描：每个种子都调用 `export` 太慢，只对新出现或有变化的种子调用；指纹计算是纯内存运算。
- 并发：每个站点 1 个下载并发；会话并发 ≤ 8；读盘任务按设备号（`st_dev`）排队，每块盘同时只做 1 个。
