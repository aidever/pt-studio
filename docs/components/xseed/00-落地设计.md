本文把征求意见稿中的方案落到可实施的程度，逐项处理实际约束：费用、信任、可迁移性（换牵线 / 换中继）、硬盘损耗，以及下载器安全、路径映射、站点适配、网络环境等其他因素。协议消息格式、状态机、DDL 留给后续 01～04 文档。

---

## 1. 范围

**v1 要做：**

- 辅种小助手 `xseed-agent`：连接 qB / TR，计算指纹，P2P 交换，下载种子，校验，加种。
- 牵线服务 `xseed-rendezvous`：运行在 Cloudflare Workers + Durable Objects 上，负责发现与信令。
- 中继 `xseed-relay`：同一套协议有两种实现，一种跑在 Cloudflare Durable Objects 上，一种是可自建的独立二进制。
- 站点侧：`crossseed-api` 插件增加会员钥匙接口和策略声明。

**v1 不做：** 部分辅种、跨文件系统复制数据、Deluge / rTorrent 适配（v2 再做）、BEP 44 DHT 存储。

## 2. 组件与部署

| 组件 | 形态 | 运行在 | 状态 |
|---|---|---|---|
| `xseed-agent` | Rust 单文件二进制 + Docker 镜像（amd64 / arm64），内置 Web UI | 用户的 NAS、盒子、PC | 本地 SQLite（加密存储凭证） |
| `xseed-rendezvous` | Cloudflare Worker + Durable Objects（SQLite 后端） | Cloudflare；也可自建（同一份代码跑在 workerd 上） | 软状态：全部可以丢失后重建 |
| `xseed-relay` | ① Durable Object WebSocket 中继 ② 独立二进制（Rust，WebSocket + QUIC） | Cloudflare / 社区 VPS | 无状态 |
| 站点侧 | `crossseed-api` 新增 `GET /v1/group-key`、`/.well-known/pt-xseed` | PT Studio 站点 | 会员钥匙每周轮换 |

## 3. 费用

### 3.1 Cloudflare 免费与付费额度（2026-11 查阅官方文档）

| 项 | 免费版 | Workers Paid（$5/月） |
|---|---|---|
| Worker 请求 | 10 万次/天；每次调用 CPU 时间 10 ms | 每月含 1000 万次 |
| Durable Objects 请求 | 10 万次/天（收到的 WebSocket 消息按 20 条计 1 次） | 每月含 100 万次，超出 $0.15/百万 |
| Durable Objects 运行时长 | 13,000 GB·s/天 | 每月含 40 万 GB·s |
| Durable Objects SQLite 读行 | 500 万行/天 | 每月含 250 亿行 |
| Durable Objects SQLite 写行 | **10 万行/天** | 每月含 5000 万行，超出 $1/百万 |
| Durable Objects SQLite 存储 | 共 5 GB | 每月含 5 GB，超出 $0.20/GB |
| TURN | 每月 1000 GB（与 SFU 共用） | 超出 $0.05/GB |
| STUN | 免费，不限量 | 同左 |

免费版超额时，相关请求直接报错，**不会产生费用**；TURN 超额则会计费。

### 3.2 成本最大的环节和对应设计

最容易超额的是**牵线服务的写行数**：每台设备都要登记自己有哪些内容。我们用以下设计压低写入：

| 设计 | 说明 | 效果 |
|---|---|---|
| **只在内容变化时登记，另加心跳** | 内容登记的有效期为 30 天，只有新增或删除内容时才写入；设备每天写 1 行心跳（`mailbox, alive_until`），查询时过滤掉心跳过期的设备 | 写入量从“整个资源库 × 刷新次数”降到“首次全量 + 每日增量” |
| **对称交换 + 只查新增内容** | 每次对话中双方**互相**提供共同站点的映射。新加入的持有者主动查询时，老持有者也顺带拿到新映射，所以每台设备只需查询**新增的本地内容**，不用定期全量重查 | 查询量约等于每天新完成的种子数 |
| **按分片批量处理** | 按桶号把数据分到 256 个分片 Durable Object，一台设备在一个分片上的登记和查询都合并为一次请求 | 请求数 ≤ 256 × 操作次数，通常远小于这个数 |
| **WebSocket 休眠** | 设备与信箱之间的长连接使用 Hibernation API，空闲时不计运行时长 | 在线设备几乎不产生时长费用 |
| **TURN 默认关闭** | 默认使用 Durable Object 中继（超额报错、不扣钱） | 避免意外账单 |

### 3.3 规模估算（每台设备 3000 个种子，每天新增 20 个）

| 规模 | 写行 | 读行 | 请求 | 结论 |
|---|---|---|---|---|
| 试运行：300 台设备，每天新加入 20 台 | 首次登记 6 万行 + 增量 6000 行 + 心跳 300 行，约 6.6 万行/天 | 约 6 万行/天 | 约 2 万次/天 | **免费版可以承受** |
| 正式运营：1 万台设备 | 一次性 3000 万行；之后增量 20 万行 + 心跳 1 万行，每月约 630 万行 | 每月约 6000 万行 | 每月约 600 万次（Durable Objects 超出含量部分约 $1） | **Workers Paid 约 $6/月**，一次性全量要分批进行，单月写行控制在 5000 万以内 |
| 中继流量 | 每次交换约 20 条消息，每条约 1 KB | — | 每次交换约 1 次 Durable Object 请求 | 可以忽略 |

估算按“每个桶内约 5 个持有者、每次查询读 1 行心跳”计算；上线前要用压测校准。

### 3.4 谁来付费、超额时怎么办

- 项目官方部署一套，费用由维护者承担或接受捐赠；**任何人都可以部署自己的一套**（见 §5）。
- 免费版超额后会在当天 UTC 0 点前返回错误：小助手指数退避，自动切换到下一个牵线服务，Web UI 显示“牵线服务今日已满载”。
- **站点侧成本**：会员钥匙接口每人每周调用 1 次；每次成功辅种下载 1 个种子，和手动下载一样。下载挑战（不配合站点使用）会额外下载 1 个种子，所以每台设备每个站点每天的挑战次数要设上限（§8.4）。

## 4. 信任

逐个列出每一方能做什么坏事，以及我们的应对：

| 角色 | 能做的坏事 | 做不到的 | 应对 |
|---|---|---|---|
| **牵线服务运营方** | 看到 IP、登记的桶号（指纹 hash 的前 16 位）、通信时间；可以拒绝服务、丢弃登记；如果它**自己也有某份文件**，可以算出那份文件属于哪个桶，从而推断“这个 IP 可能有这份文件”（同桶约十几份内容，无法确定） | 读取任何对话内容；冒充任何一方（握手密钥来自文件指纹，它没有）；知道站点和种子编号 | 只登记 16 位前缀（k-匿名）；代码开源，构建可复现；支持多个牵线服务，用户也可以自建 |
| **中继** | 看到双方 IP、流量大小和时间 | 读取或篡改内容（Noise 加密，篡改会导致解密失败） | 支持自建；多个中继中选择；中继无状态 |
| **对话对方（其他用户）** | 发送假映射；把对话拖慢；如果对方是**某站管理员假扮的普通用户**，可以把你的 IP 和“你有这份文件”联系起来，再和你随后在该站下载种子的记录对照 | 拿到你在其他站的信息；拿到你的账号或 passkey；损坏你的文件 | 假映射：下载种子后先比对结构指纹，不一致就记差评，不入库，**不读一个字节**。管理员钓鱼：提供“只走中继”模式隐藏 IP；Web UI 明确告知“对方能看到什么”。拖延：每个阶段都设超时 |
| **小助手软件本身**（供应链） | 它持有站点凭证，而且能操作下载器：被投毒的版本可以偷 passkey、删种子 | — | 开源；构建可复现；发布签名（minisign），校验通过才更新，**不静默自动更新**；凭证加密存储；下载器操作走白名单（§7.1） |
| **站点** | 拒绝签发会员钥匙；从下载记录推断哪些用户在辅种 | 看到你在其他站的情况 | 推断辅种属于正常现象，下载种子本来就会留记录；站点可以声明不参与，小助手遵守 |
| **项目维护者** | 往引导列表里塞入恶意的牵线服务或中继 | 突破端到端加密 | 即使牵线和中继是恶意的，也只能做表中第一行的事；用户可以覆盖引导列表 |

**结论：** 系统中没有任何一方需要被完全信任。牵线服务是“半可信”的，最坏情况是拿到“某 IP 可能持有某份已知文件”这种模糊推断，而且可以通过自建或多实例分散。这一点要在征求意见稿和 Web UI 中如实写明。

## 5. 可迁移性：换牵线、换中继

| 设计 | 说明 |
|---|---|
| **全部是软状态** | 牵线服务上的登记、信箱、心跳都可以丢失：换一个牵线服务后，小助手会重新登记全量内容（受 §3 的写入限额约束，按天分批）。没有需要迁移的数据 |
| **签名的引导列表** | 列表内容是牵线服务、中继、STUN 地址及优先级，用项目密钥签名（minisign）。发布在多个镜像上：GitHub Releases、GitHub Pages、Cloudflare Pages、Gitee。小助手每天拉取一次，签名不对就丢弃 |
| **用户可以覆盖** | 配置文件中的 `rendezvous[]`、`relays[]` 优先于引导列表；可以完全只用自建服务 |
| **同时用多个** | 登记：主牵线服务 + 至多 1 个备用（写入成本翻倍，可以关闭）。查询：并行查询所有已配置的牵线服务，结果合并去重 |
| **健康检查与切换** | 每 10 分钟探测一次延迟和可用性；连续 3 次失败就降级；中继按“延迟 + 最近成功率”排序 |
| **国内可达性** | `*.workers.dev` 在国内经常无法访问，官方部署必须绑定**自定义域名**；Cloudflare TURN 在国内会接到境外节点。所以 v1 就要提供可自建的 `xseed-relay` 二进制，鼓励社区部署国内节点；牵线服务也可以用 workerd 自建 |
| **协议版本** | 所有服务通过 `/.well-known/xseed` 声明支持的协议版本；小助手只使用双方都支持的最高版本 |

## 6. 硬盘损耗

### 6.1 各环节的读盘量

| 环节 | 读盘量 | 说明 |
|---|---|---|
| 计算结构指纹 | **0** | 文件列表和大小从下载器 API 获取，不读数据 |
| 计算 `content_fp` | **0** | 通过 qB 的 `torrents/export` 或 TR 的 `.torrent` 文件读取种子元数据 |
| 现场抽查（锁 2） | 每次对话约 3 × 16 KB | 量很小，但**可能唤醒已休眠的机械硬盘**，见 6.2 |
| 加入前预检 | 约 4 个 piece，最多 64 MB | 下载种子后先随机抽 4 个 piece 本地比对，不一致就放弃，**避免一次注定失败的全量校验** |
| 全量校验 | **整个内容读一遍** | 唯一的大头，见 6.3 |
| 做种上传 | 按实际上传量 | 这是辅种的目的；种子变多会增加随机读 |

### 6.2 保护休眠的机械硬盘

- **工作时间窗**（默认 02:00–08:00，可以配置）：窗外不回答抽查，返回“忙”，对方稍后重试；也不进行全量校验。
- **批量处理**：同一块盘的抽查和预检集中在窗内一次完成，盘只唤醒一次。
- 用文件所在的设备号（`st_dev`）区分不同硬盘，每块盘单独排队。

### 6.3 控制全量校验

| 措施 | 默认值 |
|---|---|
| 每块盘同时只校验 1 个种子（排队） | 开启 |
| 每块盘每天的读取预算 | 500 GB |
| 先校验什么 | 体积小的优先、站点优先级高的优先 |
| 预检失败就不进行全量校验 | 开启 |
| `content_fp` 相同时免校验 | **默认关闭**。piece hash 完全相同、原种子已 100% 完成时，数据其实已经按同一组 hash 校验过，跳过校验在技术上是安全的。但很多站点明令禁止跳过校验，所以只作为用户自担风险的选项 |

### 6.4 磁盘空间

- **只用硬链接，绝不复制数据。** 源文件和目标路径不在同一个文件系统时，按以下顺序处理：如果目录结构完全一样，就直接复用原保存路径（两个种子指向同一份文件，不需要任何链接）；否则支持 reflink 的文件系统（Btrfs / XFS）用 reflink；都不行就**跳过**，并在 Web UI 中说明原因。
- 硬链接只在 `link_dir` 中创建，删除辅种种子时只删链接。

## 7. 其他实际因素（补充）

### 7.1 下载器安全（最关键）

辅种工具最常见的事故是**误删数据**和**意外下载**，所以操作规则写死在代码里：

| 规则 | 原因 |
|---|---|
| 新种子一律以**停止状态**加入，`autoTMM=false`，显式指定保存路径 | 防止 qB 的自动管理移动文件；防止校验前就开始下载 |
| 校验完成后进度 **== 1.0** 才启动，否则删除种子 | 不完整就开始，会变成下载 |
| 删除种子时**永远**带 `deleteFiles=false` | 数据属于原种子；带上就是事故 |
| 只操作自己加入的种子（带 `xseed` 标签或分类），而且只操作本地数据库里有记录的 | 不碰用户的其他种子 |
| 加入前检查 info_hash 是否已存在于下载器 | 避免和 IYUU、cross-seed 等工具重复 |
| 全部操作幂等，可以中断恢复 | 小助手重启后继续，不会重复添加 |
| 首次运行默认**试运行模式**：只列出“会辅种什么”，不实际添加 | 让用户先看清楚，建立信任 |

### 7.2 路径映射（Docker）

小助手和下载器常常运行在不同容器中，同一个文件在两边的路径不一样。配置项 `path_map: [{downloader: "/downloads", agent: "/mnt/media"}]` 用于转换；启动时自动抽样检查：用下载器报告的路径在本地 stat，大小对得上才算配置正确，否则在 Web UI 中提示。

### 7.3 站点适配

| 问题 | 方案 |
|---|---|
| 识别种子属于哪个站 | 社区维护的**站点定义库**（YAML，带签名，随引导列表分发）：announce 域名 → 站点 ID、下载地址模板、种子 ID 的提取规则 |
| 种子 ID 从哪来 | 依次尝试：comment 字段里的详情页链接 → 站点的 pieces-hash 接口（NexusPHP）或 `crossseed-api` → 都没有就不登记这个站点的映射 |
| 下载凭证 | passkey 链接、RSS key 或 Cookie，按站点定义使用，只保存在本地 |
| 下载频率 | 每个站点单独限速（默认每分钟 2 个、每天 200 个，可按站点覆盖），并加随机间隔，避免突发 |
| 站点状态变化 | 下载返回 404 或“种子已删除”时把映射标记为失效；下载器中 tracker 报 `unregistered` 时撤销自己的登记 |
| 站点策略 | 读取 `/.well-known/pt-xseed`：`p2p: deny` 的站点既不登记也不查询；拿不到策略文件的站点按用户的设置处理（默认参与，可逐个站点关闭） |

### 7.4 Tracker 与反作弊兼容

- 大量辅种者会同时上线做种：加种后随机延迟 0–10 分钟再启动，把 announce 错开。
- “第一次 announce 就是做种状态”是辅种的正常特征：PT Studio 的 anticheat 规则集要加入这个场景的回测样例（见上一轮讨论的辅种判定）；其他站点在征求意见时提醒。

### 7.5 网络环境

| 情况 | 处理 |
|---|---|
| 有 IPv6 | 优先使用，基本都能直连 |
| 普通 NAT | STUN 探测地址 + UDP 打洞（QUIC） |
| 对称 NAT 或运营商大内网 | 打洞成功率低，直接走中继 |
| 封了 UDP | 中继走 WebSocket over TLS 443 端口 |
| 需要代理才能访问 Cloudflare | 支持 HTTP / SOCKS5 代理（仅用于访问牵线服务和中继；直连 P2P 不经过代理） |
| 隐私模式 | 只走中继，对方看不到你的 IP |

### 7.6 冷启动与“只查不答”

- 对称交换（§3.2）保证老用户也能从新用户的查询中受益，不需要额外的激励机制。
- 默认“既查询也应答”；用户可以关闭应答，但关闭后每天的查询次数减半，作为温和约束，避免只索取不贡献。

### 7.7 本地安全与隐私

- 站点凭证用系统密钥环加密，没有密钥环时（Docker）用口令派生密钥；数据库文件权限 600。
- 日志默认脱敏：不记录 passkey、完整指纹、对方 IP。
- Web UI 默认只监听 `127.0.0.1`；对外开放必须设置密码。

### 7.8 资源占用

目标：空闲时内存 < 60 MB、CPU 约等于 0，能在 ARM 的 NAS 上跑；指纹计算只做元数据运算。

### 7.9 时钟与会员钥匙

- 会员钥匙按 ISO 周轮换，同时接受**本周和上周**两把，容忍时钟偏差与交接期。
- 小助手启动时检查本地时间，和牵线服务的时间相差超过 5 分钟就在 Web UI 中警告。

### 7.10 滥用与限流

| 对象 | 限制 |
|---|---|
| 牵线服务登记 | 每个 IP 每天的新信箱数有上限；新信箱首次登记需要完成一个工作量证明（约 1 秒的计算），提高批量注册的成本 |
| 探测消息 | 每个信箱每分钟收到的探测数有上限，超出的丢弃 |
| 应答方 | 每天的应答次数、每个对象的失败次数有上限，失败太多的对象在本地拉黑 |
| 下载挑战 | 每个站点每天最多发起 / 回答 20 次，防止拿挑战刷站点下载量 |

### 7.11 同一用户的多台设备

每台设备各自运行一个小助手，互不感知。同一份内容可能在两台设备上各辅一次，这是用户自己的配置问题。Web UI 中提示：同一套下载器只运行一个小助手。

### 7.12 合规

- 系统不传输任何影音文件数据，只传输站点和种子编号。
- 官方部署前，要逐条对照 Cloudflare 服务条款中关于 Workers 和 Realtime 的使用限制；中继传输的只是小消息，预期合规，但要有书面结论。
- 尊重站点意愿：声明了 `deny` 的站点一律不参与。
